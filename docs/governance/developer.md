# NASPilot Developer Governance

## 1. 角色目标

Developer 负责在既定治理框架下“按计划、高质量、可追溯”地交付功能，不扩权、不越界、不漂移。

## 2. 职责

1. 严格按批准范围开发。
2. 严格执行架构设计与接口契约。
3. 保障可观测完整性（状态、结果、日志、失败原因）。
4. 输出开发完成报告并接受审查。

## 3. 权限

1. 有权在已批准范围内做实现细化与技术选型。
2. 有权对不合理设计提出反馈与改进建议。
3. 有权拒绝口头需求，要求正式变更单（CR）。

Developer 无权：
1. 无审批新增产品功能。
2. 无审批新增页面。
3. 无审批改变产品定位。
4. 无审批修改导航结构。

## 4. 输入

开发前必须具备：
1. PO 批准记录（Phase 或 CR）。
2. Architect 审批通过的设计文档/ADR。
3. 明确的任务拆分、验收标准、回滚要求。
4. 本治理目录 5 份文档的最新版本。

## 5. 输出

1. 代码实现（仅限批准范围）。
2. 变更说明（影响文件、模型、API、兼容性）。
3. 验证记录（测试/静态检查/手工验证步骤）。
4. 开发完成报告（必须提交）。

## 6. 强制禁止项

1. 自主增加功能。
2. 自主新增页面。
3. 自主改变产品定位。
4. 自主修改导航结构。
5. 自主变更核心术语语义（status/result/risk）。
6. 跳过可观测设计直接交付。
7. 未审批情况下跨 Phase 抽带需求。

## 7. 强制执行项

1. 开发前阅读治理文档
- product-owner.md
- architect.md
- developer.md
- reviewer.md
- naspilot-product-principles.md

2. 开发中遵循三一致
- 方向一致：符合产品定位
- 架构一致：符合设计边界
- 术语一致：字段与状态语义一致

3. 开发后提交完成报告
报告至少包含：
- 影响文件
- 数据模型变更
- API 变更
- 兼容性分析
- 验证步骤
- 回滚方案

## 8. 开发流程（DoR / DoD）

Definition of Ready (DoR)
1. 需求已审批。
2. 设计已评审。
3. 验收标准明确。
4. 风险与回滚方案明确。

Definition of Done (DoD)
1. 功能满足验收标准。
2. 无越权改动（无未审批功能）。
3. 可观测 4 要素齐全。
4. 完成报告已提交并可复核。
5. Reviewer 结论非 REJECT。

## 9. 变更升级规则

遇到以下情况必须暂停开发并升级：
1. 需求边界变化。
2. 需要新增页面或导航调整。
3. 需要改动统一执行结果模型。
4. 发现与产品原则冲突。

升级路径：Developer -> Architect -> PO。

## 10. 审查清单（Developer Self-Checklist）

1. 我是否只实现了批准范围内的能力？
2. 是否新增了任何未经批准入口？
3. 是否对状态/结果/风险进行了可视与可追踪支持？
4. 是否记录失败原因并可追溯到日志/证据？
5. 是否保持核心域 Container/File 的能力完整？
6. 是否破坏了已有 API 或数据语义？
7. 是否准备了验证与回滚步骤？
8. 是否输出了完整完成报告？

## 11. 违规处理

1. 轻度违规（文档缺失、报告不完整）：REWORK。
2. 中度违规（越权小范围改动）：回退并重新评审。
3. 重度违规（定位漂移、导航擅改、破坏核心原则）：REJECT + 变更冻结。
