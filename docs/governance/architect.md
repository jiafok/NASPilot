# NASPilot Architect Governance

## 1. 角色目标

Architect 负责将产品目标转化为稳定、可扩展、可观测的系统结构，确保 NASPilot 长期演进不出现架构漂移。

## 2. 职责

1. 信息架构（IA）
- 定义 8 个一级模块及其职责边界：Dashboard / 任务中心 / 集成工具 / 容器管理 / File Manager / 日志中心 / AI 助手 / 系统设置。
- 维护导航层级、入口唯一性与跨域跳转规则。
- 插件管理收纳至系统设置 > Integrations，不再保留独立 Plugin Center。
- 最终信息架构以 FINAL_INFORMATION_ARCHITECTURE.md 为准。

2. 页面架构
- 定义页面类型：Dashboard、Domain Home、Detail、Run Result、Log、Settings。
- 保证页面职责单一，禁止“万能工具页”。

3. 数据模型
- 定义核心实体、关系、生命周期、状态机。
- 保证领域术语统一（如 status/result/error/reason）。

4. 组件关系
- 定义前后端模块边界、依赖方向、复用策略。
- 控制耦合与重复实现。

5. 可观测体系
- 为每个新能力定义 4 要素：状态、结果、日志、失败原因。
- 建立统一执行结果标准与跨域观测视图。

## 3. 权限

1. 有权要求需求先补齐架构文档再进入开发。
2. 有权否决违反边界、引入重复入口、破坏一致性的设计。
3. 有权要求合并重复能力，拒绝平行实现。
4. 有权定义“必须走架构评审”的变更清单。
5. 有权要求在上线前补齐可观测性缺口。

## 4. 输入

1. PO 批准的需求与 Phase 范围。
2. 现有 IA、架构审计、观测架构文档。
3. 运行事件、故障复盘、性能瓶颈数据。
4. Reviewer 的问题清单与重构建议。

## 5. 输出

1. Architecture Decision Record (ADR)。
2. IA 变更说明与导航影响评估。
3. 数据模型变更说明（兼容性、迁移、回滚）。
4. 接口契约（请求、响应、错误码、版本策略）。
5. 可观测设计清单（状态、结果、日志、失败原因映射）。

## 6. 如何设计

采用 DDD-lite + Contract First + Observability First。

1. Domain First
- 先识别业务域与聚合边界，再定义页面与 API。
- 禁止先画页面后补领域模型。

2. Contract First
- 先定义接口与统一结果模型，再实现逻辑。
- 统一结果最少包含：
  - domain
  - status
  - result counters
  - started_at / ended_at
  - failure_reasons
  - evidence_refs

3. Observability First
- 任一能力必须在设计稿中回答：
  - 状态如何展示？
  - 执行结果如何归档？
  - 日志如何追溯？
  - 失败原因如何归因？

4. Navigation Integrity
- 单一入口原则：同一能力仅允许一个一级入口。
- 跨域入口必须通过“关联入口”声明，不得复制主入口。

5. Compatibility by Default
- 新接口优先增量新增，不破坏旧路径。
- 变更必须附兼容期、弃用计划、回滚策略。

## 7. 如何评审设计

使用 ARB（Architecture Review Board）流程：

1. 预审（作者自检）
- 设计文档完整性检查
- 原则符合性自评分

2. 正审（Architect 主持）
- 领域边界评审
- 信息架构评审
- 数据模型与契约评审
- 可观测性完备性评审

3. 结论
- APPROVED
- APPROVED WITH ACTIONS
- REJECTED

4. 关闭条件
- 所有 Action Items 有 owner、截止时间、验证记录。

## 8. 必须经过架构评审的改动

以下改动必须先评审后开发：

1. 新增一级导航或改动主导航结构。
2. 新增业务域、重命名核心业务域。
3. 新增/删除核心实体，或改变实体关系。
4. 改动统一执行结果模型字段语义。
5. 改动可观测主链路（状态、结果、日志、失败原因）。
6. 引入跨域聚合页面（如统一控制台、跨域总览）。
7. 接口破坏性变更（字段删除、语义变化、路径替换）。
8. 引入新的长期基础设施依赖。

## 9. 审查清单（Architect Checklist）

1. 是否明确业务域归属和边界？
2. 是否符合 Dashboard 作为运维中心的定位？
3. 是否避免重复入口与重复能力？
4. 数据模型是否有状态机与错误语义定义？
5. API 是否具备版本与兼容策略？
6. 可观测 4 要素是否齐全？
7. 是否定义失败路径与恢复路径？
8. 是否定义容量、性能、故障退化策略？
9. 是否有回滚与迁移方案？
10. 是否提供可执行验证步骤？

## 10. 架构红线

1. 不允许以临时页面替代领域建模。
2. 不允许新增“孤立工具入口”。
3. 不允许无日志、无失败原因的功能上线。
4. 不允许未评审的导航变更进入主分支。
5. 不允许破坏核心域（Container/File）可见性.
